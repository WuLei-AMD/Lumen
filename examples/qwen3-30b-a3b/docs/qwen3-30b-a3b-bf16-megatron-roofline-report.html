Qwen3-30B-A3B BF16 理论性能上限

三层时间分开读：芯片峰值给出不可越过的 1.31 s，Primus 给出另一套软件栈的 4.13 s 解析包络，本机 FlyDSL + OPUS 路径的实测是 9.88 s。下文用模型形状核对 23 GFLOP/token，并用已经跑过的 kernel 时间说明 4.13 s 不是这条路径的下一跳。

1. 结论

一次 step 有 1,048,576 个 token。芯片屋顶是 1.31 s，那要求每个 FLOP 都跑在 2.3 PFLOP/s 上，通信和 permute 的时间都是 0。这条 FlyDSL + OPUS + RCCL 路径到不了。已经测到的最快是 9.88 s（305 TFLOP/s/GPU，峰值的 13.3%）。按现有 kernel 还能挤的空间，比较可能落在 7.5–8 s。再短会先撞上 all-to-all 流自己的 5.3 s：4608 次集合通信串在一条流上，RCCL 参数和另外几条传输都没有把它缩短。5.3 s 以下要换集合通信，不是再叠一层 overlap。
为什么不是 4.13 s：Primus 那个数使用 DeepEP 和 Turbo GEMM，比这条路径的 all-to-all 流还短，所以它不是本栈的下限。10.66 s 那次 profile 设备忙约 97%，空闲大约 0.3 s，调度气泡已经不大。计算链现在大约 8–9 s，长于 all-to-all 的 5.3 s，墙钟跟着计算走。

3. Roofline 基础与芯片绝对屋顶

计算公式

AI = FLOPs / HBM Bytes P_roof(AI) = min(2.3 PFLOP/s, 8.0 TB/s × AI) Ridge Point = 2300 / 8 = 287.5 FLOP/Byte T_lower_bound = max(FLOPs / P_peak, Bytes / BW_peak)

23 GFLOP/token 不是随便取的整数。用本模型形状数一遍，和日志里的 TFLOP/s 对得上：9.88 s 那一跑报了 305.3 TFLOP/s/GPU，反推正好是 23.0 GFLOP/token。

每个 token、每一层的前向（2×MAC）： QKV 2×2048×5120 = 21.0 MFLOP O 2×4096×2048 = 16.8 MFLOP 因果 SDPA 2×32×128×4096 = 33.6 MFLOP 8 个专家 8×(2×2048×1536 + 2×768×2048) = 75.5 MFLOP router 2×2048×128 = 0.5 MFLOP 48 层前向 = 7.07 GFLOP LM head 2×2048×151936 = 0.62 GFLOP 训练把线性层按 ×3（前向 + dgrad + wgrad）、 attention 矩阵和 LM head 同样按 ×3： 线性 113.8 MFLOP ×3 ×48 = 16.38 GFLOP SDPA 33.6 MFLOP ×3 ×48 = 4.83 GFLOP LM head 0.62 ×3 = 1.87 GFLOP 合计 ≈ 23.1 GFLOP/token step FLOPs = 23e9 × 1,048,576 8 × 2.3e15 = 18.4 PFLOP/s 芯片屋顶 = 1.31 s

5. Primus 单节点模型上限

Primus 使用 Origami 对 gfx950 GEMM 建模，并使用 FAv3 SDPA 解析模型；配置为 TP=PP=CP=1、EP=8、MBS=2、SEQ=4096。模型的 48 层均为 MoE 层。

单节点上限

16 microbatches × 257.36 ms + overlapped grad AR residual 4.6 ms + optimizer 10.8 ms = 4.133 s / step 1,048,576 tokens ÷ 4.133 s = 253.7k tokens/s/node = 31.7k tokens/s/GPU

31.7k tokens/s/GPU 是芯片屋顶 100k 的 31.7%。这个数字已经扣了 Origami 的形状利用率，但通信模型是 DeepEP，attention / grouped GEMM 是 Turbo。本栈是 RCCL all-to-all 加 FlyDSL。FlyDSL 专家反向大约 3.1 ms/次（768 次/step），表中 MoE MLP 反向是 1.75 ms。只这一项，本栈就比这张表慢大约 1.4 ms × 768 ≈ 1.0 s 的 GPU 时间，而且其中只有一部分能被别的 microbatch 盖住。因此 4.13 s 是更乐观软件栈的包络，不是 FlyDSL 路径的预测值。

7. 这台机器上这条路径的上限

数字来自 profile-flydsl-opus-step11（atomic16、Q RMSNorm、router bf16 之前的那一档，墙钟约 10.7 s）和之后测到的 9.88 s。Profile 的 self CUDA 合计 15.7 s，其中 NCCL 包装和 kernel 各记了一次约 5.8 s；扣掉这次重复后，GPU 上的 kernel 时间大约 9.9 s，和 10.7 s 的设备时间对齐，重叠掉的主要就是 all-to-all。

计算链现在比通信流长。专家前后向大约 3.4 s，attention 大约 1.2 s（atomic16 之后反向主 kernel 还会再短一截），QKV 和输出投影大约 1.4 s，LM head 0.24 s，permute / sort / 逐元素大约 2 s。这些大部分前后依赖，加起来大约 8–9 s，长于 all-to-all 的 5.3 s，所以墙钟跟着计算走。9.88 s 和这个估计相符：overlap 还能拿的就是 profile 里那大约 0.3 s 空闲。

各块还能短多少

  • 专家 GEMM，大约还能少 0.7 s GPU 时间。FlyDSL 反向 2.37 s、前向 0.98 s。rocprof 在同样的 16 专家、8192 token 形状上，前向两段 GEMM 是 730 / 564 TFLOP/s，反向 NN / TN 是 563 / 462 TFLOP/s，按 FLOP 折回来大约 2.6 s。孤立采样和训练 step 之间还差这 0.7 s，主要是 ragged 的专家长度和反向的四次 grouped launch。再往下要新 kernel，不是把现在的 kernel 重新调度。
  • Attention 剩下的空间小于 0.2 s。OPUS 前向 227 ms（768 次，296 µs）。反向主 kernel 在改 atomic16 之前是 857 ms；那一次改动已经把墙钟降下 0.30 s。rocprof 里这条反向是 695 TFLOP/s，和现在的耗时同一量级。
  • QKV / 输出投影几乎到头了。hipBLASLt 上这 6 个形状再换 tile，六次加起来大约 20 ms 墙钟。LM head 的 48 次 aten::mm 共 239 ms，大约 1 PFLOP/s，不是缺口。
  • Permute、sort、残差加，账面上大约 2 s，但融合没有换成墙钟。Q RMSNorm 已经留下 0.34 s。K 的行数只有 Q 的八分之一，换 Triton 更慢。残差加进下一层 norm 在 graph replay 上要么算错，要么更慢。
  • All-to-all 的 5.3 s 不是带宽打满。一次 dispatch 的有效载荷大约是 200 MB 量级（8192 token × top-8 × 7/8 出卡 × 2048×2 字节）。1.16 ms 的平均调用里，大消息本身可以更快，小的 count 交换则是延迟。4608 次串行之后，总时间停在 5.3 s。这就是这条通信实现的底。

8. 仍然值得做的顺序

下面按已经发生的训练结果改写，不再把「离屋顶远」直接翻译成「再做 overlap」。

  1. 9.88 s 相对 1.31 s 的差距，大部分是 kernel 还慢，不是 GPU 在等。10.66 s 那一档（atomic16 之前）的 step 11 profile：设备跨度 10.66 s，忙 10.34 s，空闲 0.32 s。再把通信和计算叠一层，天花板就是这 0.3 s。
  2. 专家 GEMM 仍然是最大的计算项，而且 FlyDSL 已经吃过一轮。孤立采样里 GEMM1/GEMM2 只有计算屋顶的 25–32%。端到端里 FlyDSL 反向大约 3.1 ms/次，前向大约 1.3 ms/次，768 次合计大约 3.4 s GPU 时间。Primus 那张表更乐观。下一刀如果还在专家上，得比现在的 FlyDSL kernel 更快，而不是把同一个 kernel 再调度一次。
  3. TN 在拐点左边，但没有贴住 HBM。1.76 TB/s 对 8 TB/s。先减流量会漏掉 tile 和尾波；等 kernel 真的靠近 8 TB/s 再谈流量。
  4. Attention 前向可以少投，反向的原子加还不能算做完。OPUS 前向 45.8% 的屋顶效率是表里最高的，端到端只值 0.42 s。反向从 fp32 atomic 改成 atomic16，同一条路径上又少了 0.30 s。旧结论「不必再碰 attention」只覆盖了前向。
  5. 路由索引是低算术强度，但几次融合没有变成墙钟。残差加进 RMSNorm、层内把 all-to-all 切块、IPC 可变长 all-to-all，都试过。前两个更慢或直接出错，第三个把 step 拖到大约 29 s。Q RMSNorm 是这里面真正留下的 0.34 s，而且只换了 Q。
  6. 第 6 节的 32 节点曲线先不要用来排期。固定 GBS=256 到 16 节点就没有 microbatch 可拆，这句几何关系是对的。99% 弱扩展效率来自 Primus 默认拓扑，不是这台机器的网络测量。单节点还在 9.88 s 时，多节点效率不是当前的限制项。

9. 限制与复现口径

  • 9.88 s、305 TFLOP/s/GPU、13.3% MFU 来自 qwen3-30b-a3b-sonic-flydsl-opus-attnbwda16-mbs2-gbs256-seq4096-mbs2-gbs256.log 的 steps 11–20 中位数。atomic16 默认关闭，不设环境变量时同一路径是 10.17 s。
  • Primus 配置启用 Turbo Attention、Turbo grouped GEMM、DeepEP 与 sync-free MoE stage 2。4.13 s 保留为对照包络，不再写成这条 FlyDSL + OPUS + RCCL 路径的可执行上限。
  • Primus 默认硬件拓扑模型在 2–32 节点给出近乎固定的梯度 AllReduce 时间，因此 99% 弱扩展效率应视为“模型内理想包络”，必须用目标集群网络 benchmark 再收紧。
  • 单节点 benchmark-anchored Primus 投影未完成；当前运行环境缺少完整 Primus benchmark 依赖。报告保留纯模拟结果并明确标注，未填造 artifact。
  • 知乎页面受反爬限制；报告采用文章所述的标准 Roofline 方法，不引用无法核验的文章专有数值。
